# C-Phoenix Graphs

This directory contains generated Graphviz source (`.dot`), rendered SVG, and
short Markdown guides. Regenerate the design-time graphs from `c-phoenix/`
with `make docs`; they describe source structure, not a particular playthrough.

## Start here: how the C port is laid out

`file_callgraph` is the readable overview — which source file depends on which,
grouped into the port's architectural clusters:

![Which C source files depend on each other, grouped into clusters: game state, entity logic, collision mechanics, rendering, audio, utilities and core architecture](file_callgraph.svg)

That picture is the fastest way to get oriented: entity logic in the middle,
collision and scoring above it, platform and audio at the bottom right, and
`utilities.c` pulled on by nearly everything.

## The full set

| Graph | Kind | Generator | What it answers |
| --- | --- | --- | --- |
| [callgraph](callgraph.md) | Design-time | `tools/generate_callgraph.py` | Which C functions call each other? |
| [file_callgraph](file_callgraph.md) | Design-time | `tools/generate_file_callgraph.py` | Which source files depend on each other? |
| [func_prefix_callgraph](func_prefix_callgraph.md) | Design-time | `tools/generate_func_prefix_callgraph.py` | Which semantic function families interact? |
| [cross_domain_callgraph](cross_domain_callgraph.md) | Design-time | `tools/generate_cross_domain_callgraph.py` | Which calls cross architectural domains? |
| [internal_domain_callgraph](internal_domain_callgraph.md) | Design-time | `tools/generate_internal_domain_callgraph.py` | How cohesive is each domain internally? |
| [execution_tree_callgraph](execution_tree_callgraph.md) | Design-time | `tools/generate_execution_tree_callgraph.py` | What top-down call hierarchy is present in the source? |
| [rom_bank_callgraph](rom_bank_callgraph.md) | Design-time | `tools/generate_rom_bank_callgraph.py` | How do C functions relate to original program-ROM banks? |
| [stub_hunter_callgraph](stub_hunter_callgraph.md) | Design-time | `tools/generate_stub_hunter_callgraph.py` | Which active C callers still reach compatibility stubs? |
| [coverage_callgraph](coverage_callgraph.md) | Runtime-derived | `tools/generate_coverage_callgraph.py` | Which source-level functions were covered by imported coverage data? |

Only `file_callgraph` is shown above, deliberately. The function-level graphs
are very large — `func_prefix_callgraph` is roughly 2300 × 8100 points and
`execution_tree_callgraph` over 10 000 points wide — so a thumbnail would be an
unreadable smudge. Open those SVGs directly and zoom, rather than expecting
them to work as inline images.

`stub_hunter_callgraph.svg` currently renders empty. That is the result, not a
failure: no active C caller still reaches a ROM-compatibility stub.

## Not the same as runtime graphs

These graphs should not be confused with the per-scenario **runtime** graphs in
`context/runtimegraphs/<scenario>/`, generated by `make runtimegraph`. Those
use actual calls recorded while an input script plays. The runtime comparison
there also distinguishes designed call edges from edges observed in that run.
